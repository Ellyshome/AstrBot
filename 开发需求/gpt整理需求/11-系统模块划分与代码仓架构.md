# 2. 总体架构原则

系统采用：

```text
Modular Monolith
```

（模块化单体架构）

即：

```text
一个代码仓
一个主服务
多个业务模块
```

而不是：

```text
多个独立微服务
```

---

# 3. 为什么V1不采用微服务

当前阶段特点：

* 团队规模较小
* 业务规则快速变化
* Agent能力持续迭代
* Workflow设计尚未稳定

如果直接采用微服务：

```text
Workflow Service
Agent Service
Knowledge Service
Graph Service
Auth Service
...
```

会导致：

* 部署复杂
* 调试困难
* 开发效率下降
* 运维成本升高

因此推荐：

```text
V1：模块化单体

V2：部分服务拆分

V3：全面微服务化
```

# 6. Apps层

目录：

```text
apps/

├─ api_server
├─ worker
├─ scheduler
```

## api_server

负责：

* REST API
* WebSocket
* 用户请求入口

## worker

负责：

* 消费事件
* 执行Workflow
* 执行Agent

## scheduler

负责：

* 定时任务
* 数据统计
* 知识归档
* 自动分析

# 47. 设计结论

V1阶段采用：

```text
Modular Monolith
```

架构。

核心链路：

```text
Domain
↓
Event
↓
Workflow
↓
Agent
↓
Knowledge
```

代码组织：

```text
Monorepo
+
模块化单体
+
事件驱动
```

实现：

```text
开发简单
部署简单
演化容易
未来可拆分
```

最终形成适合企业数字大脑长期演化的工程架构。
