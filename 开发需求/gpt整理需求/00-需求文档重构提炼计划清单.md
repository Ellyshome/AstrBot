# 1. 编写目的

当前 `gpt整理需求` 目录已经包含 17 个文档，覆盖了实体模型、事件模型、权限、存储、Agent、Workflow、状态机、知识库、事件总线、技术选型、MVP 数据库、AstrBot 接入、开发任务和验收用例。

这些文档整体方向正确，但存在以下问题：

1. 长期架构和 MVP 开发范围混在一起。
2. 部分文档偏平台化，容易导致第一阶段开发范围过大。
3. AstrBot / IM 入口在前 14 个文档中权重不足。
4. 多个概念命名不统一。
5. 一些长期设计原则不适合直接作为 MVP 开发约束。
6. 缺少一套“当前阶段真正执行”的主目录结构。

因此，后续需要将现有文档重新提炼，形成一套符合当前预期的需求文档目录。

当前预期是：

```text
先尽快跑起来
以 AstrBot / IM 为第一入口
优先实现消息入库、事件录入、文件归档、会议记录、任务创建、简单查询
长期能力保留设计余地，但不阻塞 MVP
```

# 2. 总体重构原则

## 2.1 不推翻原文档

现有 01-17 文档作为原始资料和架构参考保留。

后续重构不是删除原文档，而是重新提炼一套更适合开发启动的正式需求目录。

---

## 2.2 区分 MVP 与长期架构

后续文档必须明确区分：

```text
MVP 必做
MVP 可选
V2 后置
V3 长期规划
```

避免开发者误以为所有架构设计都要第一阶段实现。

---

## 2.3 以 IM 闭环为第一入口

后续文档应明确：

```text
AstrBot / IM 是第一阶段主入口
FastAPI / Web 管理端不是第一优先级
```

Web/API 可以作为后续管理能力保留。

---

## 2.4 先做模块化单体

第一阶段不拆微服务。

采用：

```text
模块化单体
插件入口
PostgreSQL 主库
必要时接 MinIO / pgvector
```

---

## 2.5 长期能力先留接口，不强实现

以下能力第一阶段只保留接口或设计位置：

```text
Neo4j 知识图谱
完整 Workflow Engine
完整 State Machine
复杂 RBAC
多 Agent 协同
自动生成企业标准
事件总线 Outbox / DLQ
ERP/OA/CAD 集成
```

# 3. 当前文档存在的主要问题

## 3.1 问题一：长期架构与 MVP 范围混杂

涉及文件：

```text
04-知识图谱模型.md
07-业务流引擎设计.md
08-状态机设计.md
09-知识库与长期记忆架构.md
10-事件总线与系统集成架构.md
```

问题描述：

这些文档描述的是中长期平台能力，设计方向正确，但如果直接作为 MVP 开发依据，会导致第一阶段范围过大。

典型风险：

```text
还没跑通 IM 消息入库
就开始建设知识图谱、流程引擎、状态机、事件总线
```

计划修改：

1. 将这些内容重新归入“长期架构设计”目录。
2. 在每份长期设计文档开头明确标注：

```text
本文为 V2/V3 架构参考，MVP 阶段不要求完整实现。
```

3. 从 MVP 文档中只抽取必要约束，例如：

```text
PostgreSQL 是唯一事实源
Event 是核心记录对象
Agent 不能绕过权限
```

## 3.4 问题四：部分原则过于绝对，不适合 IM 场景

涉及文件：

```text
01-核心实体模型.md
02-事件模型.md
03-RBAC权限模型.md
```

问题描述：

例如现有文档中有类似原则：

```text
所有数据必须归属实体，否则禁止入库
```

该原则对正式业务数据是合理的，但对 IM 消息不完全适用。

IM 场景中会出现：

```text
未知用户消息
未识别项目消息
临时群聊消息
无法分类消息
外部人员消息
```

这些数据也必须先留痕。

计划修改：

将规则调整为：

```text
正式业务数据必须归属实体；
原始消息、异常消息、待识别数据允许先入库；
未绑定数据必须标记状态，不得直接进入正式业务闭环。
```

建议状态：

```text
pending
unbound
unknown
need_review
confirmed
```

```text

```

## 13-代码模块与文件结构设计.md

用于指导第一阶段代码落地，但只描述模块、目录、文件职责和依赖边界，不写具体实现代码。

建议覆盖：

```text
MVP推荐目录结构

integrations模块职责
domains模块职责

agents模块职责
services模块职责
infrastructure模块职责
schemas模块职责
配置与启动文件
测试目录结构
第一阶段必须实现文件
第二阶段预留模块
禁止事项
```

重点明确：

```text
plugin.py 只做 AstrBot 接入，不写业务逻辑
Router Agent 只做意图识别和分派
Handler 处理具体业务意图
Service 执行业务规则和数据库调用
Repository / Infrastructure 封装数据库与外部设施
```

同时写入禁止事项：

```text
禁止在 plugin.py 中直接写业务逻辑
禁止在 Agent 中直接拼 SQL
禁止 Handler 直接依赖 AstrBot 原始对象
禁止数据库模型与 IM 原始 payload 强耦合
禁止第一阶段创建大量空目录
禁止为了未来可能性提前拆微服务
```
