# 90-V2后续架构规划

## 1. 文档定位

本文记录 MVP 之后的后续架构规划。

本文不是第一阶段开发范围。

第一阶段不得因为本文内容扩大 MVP。

---

## 2. V2 建议扩展顺序

MVP 稳定后，建议按以下顺序扩展：

```text
计划任务提醒
文件解析与向量化
多轮补全
权限细化
LangGraph 工作流
自进化业务流审核
Neo4j 知识图谱
事件总线
```

---

## 3. 完整 RBAC

V2 可从 MVP 的 admin/member/guest 扩展为：

```text
组织角色
项目角色
资源权限
动作权限
Agent Delegation
拒绝优先
```

核心原则保持：

```text
Agent 只能继承用户权限
```

---

## 4. Workflow Engine

当固定 Handler 流程稳定后，引入 Workflow Engine。

长期设计：

```text
Workflow Definition(JSON)
→ Workflow Runtime(LangGraph)
→ Agent / Handler Node
```

MVP 中固定流程可逐步迁移为配置化流程。

---

## 5. State Machine

V2 引入状态机，用于约束：

```text
Task 状态
File 状态
Approval 状态
Workflow 状态
Project 状态
```

MVP 只用简单枚举字段。

---

## 6. 计划任务提醒

在 MVP tasks 基础上增加：

```text
定时扫描
即将到期提醒
超期提醒
销项确认
提醒日志
```

可新增 Scheduler 模块。

---

## 7. 自进化业务流审核

长期目标：

```text
未知需求识别
→ 生成临时业务预案
→ 管理员审核
→ 业务流模板入库
→ 后续复用
```

约束：

```text
AI 不得自动上线新业务流
必须管理员审核
必须版本化
```

---

## 8. Neo4j 知识图谱

V2/V3 引入 Neo4j。

用途：

```text
项目关系追踪
事件链分析
人员-项目-任务-文件关系查询
知识路径导航
```

原则：

```text
PostgreSQL 是事实源
Neo4j 是派生关系层
```

---

## 9. 事件总线

MVP 使用同步调用 + events 表。

后续演进：

```text
Redis Streams
→ Outbox
→ DLQ
→ Kafka
```

引入条件：

```text
多消费者
异步任务增多
需要可靠事件投递
外部系统接入
```

---

## 10. 知识库演化

MVP：

```text
公司制度与业务流程知识包
→ Document
→ Chunk
→ Query
```

V2/V3：

```text
Document
→ Fact
→ Knowledge
→ Case
→ Standard
```

企业标准必须人工审核后发布。

---

## 11. 多 Agent 协同

当 Handler 稳定后再拆分：

```text
Meeting Agent
Archive Agent
Planning Agent
Design Agent
Construction Agent
Cost Agent
Risk Agent
```

拆分原则：

```text
业务边界稳定
调用链可审计
权限模型清楚
有明确收益
```

---

## 12. 外部系统集成

后续可接入：

```text
OA
ERP
CAD
BIM
企业微信
邮箱
```

统一通过 Integration Layer 转为标准事件。

---

## 13. 结论

V2/V3 方向是平台化、知识化、流程化。

但前提是 MVP 已经跑通：

```text
IM 入口
消息留痕
文件 / 会议 / 任务 / 事件
简单查询
用户愿意使用
```
