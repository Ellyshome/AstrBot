# 第一阶段开发任务清单

## 1. 阶段目标

第一阶段目标是尽快跑通团队大脑 Agent 模块的最小业务闭环。

最小闭环定义：

```text
用户通过 IM 发送一条消息
→ AstrBot 插件接收
→ 系统生成 event_id
→ 通讯记录入库
→ 路由 Agent 判断意图
→ 若为事件录入，生成 flow_id
→ 创建业务流转单
→ 鉴权 Agent 做基础鉴权
→ 业务 Agent 抽取事件信息
→ 内业 Agent 写入项目事件表
→ 系统通过 IM 回复用户“已记录”
```

第一阶段只要求跑通“通用事件录入”，计划任务、自进化、文件解析可以先保留接口。

## 2. 开发原则

1. 先跑通，再完善。
2. 先单机模块化运行，暂不拆微服务。
3. 先做文本消息，图片、文件、语音后续增强。
4. 先做统一 `project_event` 主表，暂不拆大量事件子表。
5. 先做最小鉴权，复杂 RBAC 后续完善。
6. 所有关键步骤必须写日志。
7. 所有新增能力尽量通过可扩展接口保留后续空间。

## 4. M1：项目骨架与配置

### 4.1 创建模块目录

建议目录：

```text
team_brain/
  plugin.py
  config.py
  core/
  im/
  agents/
  db/
  skills/
  workflows/
```

### 4.2 配置文件

实现基础配置读取：

```yaml
team_brain:
  enabled: true
  database:
    url: "postgresql://user:password@localhost:5432/team_brain"
  agent:
    session_timeout_minutes: 30
  log:
    level: "INFO"
```

### 4.3 完成标准

- 插件或模块可以被 Python 正常导入。
- 配置可以读取。
- 日志可以输出。

### 5.2 建立 P0 表

```text
im_message
employee

business_flow_log
```

### 5.3 插入测试数据

至少插入：

1. 一个测试用户。

### 5.4 完成标准

- 可以插入和查询测试数据。

## 6. M3：IM 消息标准化与入库

### 6.1 标准化消息结构

实现 `normalize_message()`，输出：

```json
{
  "event_id": "EV-20260605-000001",
  "im_source": "qq",
  "conversation_type": "group",
  "conversation_id": "group_001",
  "sender_id": "user_001",
  "sender_name": "张三",
  "msg_type": "text",
  "content": "记录一下，今天1号楼地下室防水验收完成",
  "files": [],
  "timestamp": "2026-06-05T10:00:00"
}
```

### 6.2 通讯记录入库

由内业 Agent 或 MessageRepository 写入 `im_message`。

### 6.3 完成标准

- 用户发送一条文本消息。
- 系统生成 event_id。
- `im_message` 有记录。
- 失败时有错误日志。

## 7. M4：路由 Agent 最小实现

### 7.1 意图识别规则

第一阶段可先使用关键词规则，不必一开始就接复杂模型。

建议规则：

| 关键词 | 意图 |
|---|---|
| 记录一下 / 录入 / 上报 / 提交 / 完成 / 验收 | event_record |
| 计划 / 任务 / 截止 / 完成时间 | plan_record |
| 查询 / 查一下 / 有没有 / 什么时候 | query |
| 其他 | chat |

### 7.2 路由逻辑

```text
收到标准化消息
→ 保存通讯记录
→ 识别意图
→ chat：只回复或不回复
→ event_record：创建业务流
→ plan_record：先回复“计划功能开发中”或进入预留流程
→ query：先回复“查询功能开发中”或进入预留流程
```

### 7.3 完成标准

- 普通消息不会触发事件入库。
- “记录一下……”会识别为 `event_record`。
- 识别结果写入日志。

## 8. M5：业务流转单与流程实例

### 8.1 生成 flow_id

当路由结果为 `event_record` 时生成 `flow_id`。

### 8.2 创建业务流转单

结构：

```json
{
  "event_id": "EV-20260605-000001",
  "flow_id": "FLOW-20260605-000001",
  "flow_type": "event_record",
  "source": "im",
  "status": "processing",
  "user": {},
  "project": {},
  "intent": {},
  "payload": {},
  "logs": []
}
```

### 8.3 写入 business_flow_instance

记录：

- event_id
- flow_id
- flow_type
- status
- user_id
- project_id
- payload

### 8.4 完成标准

- 事件录入消息能创建业务流实例。
- `business_flow_instance` 有记录。
- `business_flow_log` 有“流程创建”记录。

## 9. M6：鉴权 Agent 最小实现

### 9.1 第一阶段鉴权策略

先实现简单规则：

1. 用户存在 → 允许普通事件录入。
2. 用户不存在 → 拒绝，并提示需要先录入人员信息。
3. 项目无法识别 → 允许作为“未绑定项目事件”暂存。
4. 项目主数据修改 → 暂时拒绝或要求管理员。

### 9.2 输出结构

```json
{
  "allowed": true,
  "reason": "用户存在，允许录入普通事件",
  "risk_level": "low"
}
```

### 9.3 完成标准

- 鉴权通过时继续流程。
- 鉴权失败时不写入 project_event。
- 鉴权结果写入 `business_flow_log`。

## 10. M7：通用事件录入

### 10.1 事件信息抽取

第一阶段可先抽取基础字段：

| 字段 | 来源 |
|---|---|
| event_title | 根据文本生成简短标题 |
| event_content | 原始消息内容 |
| event_type | 关键词分类，默认 other |
| event_time | 能识别则提取，否则用消息时间 |
| project_id | 能识别则绑定，否则为空 |
| reporter_id | 当前用户 |

### 10.2 事件类型规则

简单关键词规则：

| 关键词 | event_type |
|---|---|
| 日报 / 周报 | construction_daily |
| 材料 / 进场 / 验收 | material_checkin |
| 完成 / 节点 / 进度 | progress_node |
| 许可证 / 规划证 / 预售证 | certificate |
| 会议 / 纪要 | meeting_record |
| 视察 / 领导 | leader_inspection |
| 图纸 / 版本 | drawing_update |
| 合同 | contract |
| 隐患 / 安全 | safety_issue |
| 其他 | other |

### 10.3 写入 project_event

业务 Agent 生成结构化事件后，由内业 Agent 写入 `project_event`。

### 10.4 完成标准

- “记录一下，今天1号楼地下室防水验收完成”能写入 `project_event`。
- 生成 `business_no`。
- flow 状态更新为 `completed`。

## 11. M8：IM 回复闭环

### 11.1 成功回复

示例：

```text
已记录该事件。
事件编号：BUS-20260605-000001
类型：progress_node
```

### 11.2 失败回复

示例：

```text
本次记录失败：未识别到您的人员信息，请联系管理员先录入人员。
```

### 11.3 普通消息回复策略

第一阶段普通消息可以不回复，或回复：

```text
已收到。
```

建议配置开关控制，避免群聊刷屏。

### 11.4 完成标准

- 事件录入成功后，用户能收到明确回复。
- 失败时用户能知道原因。
- Agent 回复也写入 `im_message`，direction 为 `agent_to_user`。

## 12. M9：异常与日志

### 12.1 日志内容

必须记录：

- 收到消息。
- 生成 event_id。
- 消息入库。
- 意图识别。
- 业务流创建。
- 鉴权结果。
- 事件入库。
- IM 回复。
- 异常堆栈。

### 12.2 异常记录

发生以下异常时写入 `incident_record`：

- 数据库连接失败。
- 消息格式无法解析。
- 鉴权异常。
- 事件入库失败。
- IM 回复失败。
- 未知业务类型。

### 12.3 完成标准

- 常见异常不会导致程序整体崩溃。
- 异常可在日志或 `incident_record` 中追踪。

## 13. 第一阶段验收用例

### 用例 1：普通消息记录

输入：

```text
大家下午三点开个会
```

期望：

- 写入 `im_message`。
- 不创建 `project_event`。
- 可配置是否回复。

### 用例 2：事件录入

输入：

```text
记录一下，今天1号楼地下室防水验收完成。
```

期望：

- 写入 `im_message`。
- 识别为 `event_record`。
- 创建 `business_flow_instance`。
- 写入 `project_event`。
- 回复事件编号。

### 用例 3：未知用户

输入：

```text
记录一下，今天材料进场验收完成。
```

前提：发送人未在 employee 中。

期望：

- 写入 `im_message`。
- 鉴权失败。
- 不写入 `project_event`。
- 回复需要先录入人员。

### 用例 4：计划任务预留

输入：

```text
把这个计划表录入一下，下周五前完成。
```

期望：

- 写入 `im_message`。
- 识别为 `plan_record`。
- 第一阶段可回复“计划任务功能正在接入”。
- 不影响事件录入流程。

### 用例 5：数据库异常

前提：数据库断开。

期望：

- 程序记录错误日志。
- 用户收到失败提示。
- 程序不中断主进程。

```text
15. project_event 入库
16. IM 回复
17. 异常记录
18. 验收用例测试
```

## 15. 暂缓开发项

以下内容保留设计，不在第一轮最小闭环中强制实现：

1. 完整 RBAC 权限系统。
2. 多轮复杂补全。
3. 文件 OCR 与内容解析。
4. Excel 计划表自动解析。
5. MinIO 正式接入。
6. FAISS 制度检索。
7. Neo4j 知识图谱。
8. 自进化业务流管理员审核页面。
9. 多 Agent 独立进程部署。
10. 大规模并发会话池调度。

## 16. 第一阶段完成定义

当以下条件全部满足时，第一阶段可以认为完成：

1. AstrBot 能把 IM 消息交给团队大脑模块。
2. 文本消息能标准化。
3. 每条消息都有 event_id。
4. 通讯记录能写入 `im_message`。
5. 路由 Agent 能区分普通消息和事件录入消息。
6. 事件录入消息能生成 flow_id。
7. 业务流实例能写入 `business_flow_instance`。
8. 鉴权 Agent 能完成最小鉴权。
9. 业务 Agent 能生成基础项目事件。
10. 内业 Agent 能写入 `project_event`。
11. 用户能收到成功或失败回复。
12. 关键日志可追踪。

## 17. 第二阶段建议方向

第一阶段跑通后，第二阶段建议优先补：

1. 计划任务录入与提醒。
2. 文件上传与 MinIO 归档。
3. 多轮补全机制。
4. 项目识别和用户项目权限完善。
5. 业务流模板表。
6. 未知业务流临时预案和管理员审核。
