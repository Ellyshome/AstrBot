# 团队大脑 Agent 模块需求规格说明

## 1. 项目背景

本项目面向商品住宅地产开发业务，覆盖从拿地、规划设计、土建工程、销售配合、交付到结算归档的全流程信息管理场景。

当前阶段系统不追求一次性实现完整业务自动化，而是优先建设一个可运行、可扩展、可演进的 Agent 协同底座，为后续业务流持续沉淀和智能化处理打基础。

系统基于 AstrBot 项目扩展开发，主要复用 AstrBot 的多 IM 接入能力，但不使用 AstrBot 原有 Agent 作为核心业务处理器。IM 上行与下行消息通过对接层接入后，由自研路由 Agent 全量接管，并分派给各专项 Agent 处理。

## 2. 当前阶段目标

第一阶段目标是搭建团队大脑 Agent 模块的 MVP 框架，重点实现以下能力：

1. 多 IM 消息接入、监听、记录与结构化。
2. 用户身份识别、项目归属识别与基础权限校验。
3. 通用项目事件录入，包括文字、文件、图片、语音等内容的辅助结构化。
4. 计划任务录入、变更、挂起、撤下与到期提醒。
5. 基于制度、历史记录和业务流模板的业务处理引导。
6. 未知业务需求的临时预案生成、管理员审核与后续复用。

当前阶段系统主要提供：

- 信息辅助录入。
- 信息查询。
- 信息核验。
- 计划任务按时提醒。
- 通讯记录留痕。
- 业务流转过程留痕。

## 3. 非目标范围

第一阶段暂不追求以下能力：

1. 不做全业务闭环自动审批系统。
2. 不直接替代公司现有 OA、ERP、成本、工程管理系统。
3. 不做复杂合同审查、图纸审查、工程量自动核算等高风险专业判断。
4. 不允许 AI 自动上线新的业务流程，所有新业务流必须经过管理员审核。
5. 不在第一阶段强依赖完整知识图谱，Neo4j 可作为后续增强能力保留。
6. 不做过细的业务清单穷举，优先建立通用业务流框架。

## 4. 总体架构

系统采用多 Agent 专家协同架构，核心思路如下：

```text
IM 平台
  ↓
AstrBot 多 IM 连接池
  ↓
IM 对接层
  ↓
路由 Agent
  ↓
鉴权 Agent / 业务 Agent / 内业 Agent / 经理 Agent
  ↓
数据库网关 DBUtils
  ↓
PostgreSQL / MinIO / FAISS / Neo4j
```

### 4.1 IM 对接层

IM 对接层负责适配 AstrBot 与自研 Agent 系统之间的数据格式，主要职责包括：

- 接收 IM 平台上行消息。
- 标准化消息结构。
- 为每条进入系统的消息生成或绑定 `event_id`。
- 将消息交给路由 Agent。
- 接收 Agent 返回结果。
- 调用 AstrBot 或 IM 平台能力完成消息下发。

### 4.2 路由 Agent

路由 Agent 是系统的消息入口和任务分派中心，负责：

- 监听 IM 事件。
- 识别消息类型。
- 判断用户意图。
- 发起业务流转单。
- 调用鉴权 Agent。
- 将任务分派给业务 Agent、内业 Agent 或经理 Agent。
- 对未知业务请求发起自进化流程。

### 4.3 LangGraph 状态流

所有具有多步骤处理逻辑的业务流程，应使用 LangGraph 建模为状态图。

典型状态包括：

```text
idle
→ receive_event
→ auth_check
→ classify_intent
→ collect_information
→ validate_information
→ archive
→ notify
→ completed
```

异常状态包括：

```text
permission_denied
information_missing
rule_not_found
system_error
waiting_admin_review
paused
```

## 5. 核心对象定义

### 5.1 event_id

`event_id` 是系统内所有外部事件进入系统后的全局唯一流转凭证。

典型格式：

```text
EV-YYYYMMDD-00001
```

用途：

- 标识一次 IM 消息事件。
- 串联通讯记录、业务流转单、文件、异常、通知等数据。
- 支持全链路追踪和审计。

### 5.2 flow_id

`flow_id` 是业务流实例编号，表示一次具体业务处理流程。

典型格式：

```text
FLOW-YYYYMMDD-00001
```

一个 `event_id` 可以触发零个、一个或多个 `flow_id`。

例如：

- 一条普通群聊消息只生成通讯记录，不生成业务流。
- 一条“请录入今天施工日报”的消息会生成事件录入业务流。
- 一条包含计划表文件的消息可能同时生成文件归档流和计划录入流。

### 5.3 业务流转单

业务流转单是 Agent 之间传递任务的统一协议，也是业务处理过程的核心数据结构。

建议基础结构如下：

```json
{
  "event_id": "EV-20260605-00001",
  "flow_id": "FLOW-20260605-00001",
  "flow_type": "event_record",
  "source": "im",
  "status": "processing",
  "user": {
    "user_id": "user_001",
    "user_name": "张三",
    "im_source": "企业微信"
  },
  "project": {
    "project_id": "project_001",
    "project_name": "XX住宅项目"
  },
  "intent": {
    "intent_type": "event_record",
    "confidence": 0.92,
    "raw_text": "今天1号楼地下室防水验收完成"
  },
  "payload": {},
  "auth_result": {},
  "logs": []
}
```

### 5.4 业务事件

业务事件是项目过程中发生的、需要记录、归档、提醒或触发后续流程的事实。

包括但不限于：

- 新项目创建。
- 项目信息变更。
- 施工日报/周报。
- 材料进场验收。
- 进度节点完成。
- 签证变更申请。
- 证照获取。
- 图纸版本更新。
- 合同签署。
- 会议纪要。
- 领导视察。
- 安全隐患上报。
- 计划任务新增、终止、修改。

### 5.5 通讯记录

通讯记录是所有 IM 上行和下行消息的结构化存档。

通讯记录应至少包含：

- 消息 ID。
- 会话 ID。
- 群 ID 或接收人 ID。
- 发送人 ID。
- 消息类型。
- 消息内容。
- 文件列表。
- 发送时间。
- 所属项目。
- 关联 `event_id`。
- 关联 `flow_id`。

## 6. Agent 职责边界

### 6.1 经理 Agent

职责：

- 监控全局事件流和通讯流。
- 汇总异常事件。
- 处理或转交管理员处理未知问题。
- 关注计划任务状态。
- 对超期未销项任务发起提醒或催办。

可读：

- 全局事件状态。
- 计划任务表。
- 通讯记录摘要。
- 异常记录。
- 业务流转单。

可写：

- 异常处理记录。
- 提醒记录。
- 催办记录。

禁止：

- 绕过鉴权直接修改业务主数据。
- 自动批准新业务流上线。

### 6.2 路由 Agent

职责：

- 监听 IM 池消息。
- 标准化消息。
- 识别用户意图。
- 判断业务类型。
- 生成 `event_id` 与业务流转单。
- 分派任务到对应 Agent。

可读：

- 制度相关业务流。
- 人员表。
- 通讯录。
- 公司表。
- 项目基础表。

可写：

- 路由日志。
- 初始业务流转单。

禁止：

- 直接写入业务数据表。
- 直接修改项目主数据。
- 直接跳过鉴权分派高风险业务。

### 6.3 鉴权 Agent

职责：

- 根据业务流转单判断发起者是否有权限。
- 校验用户、公司、项目、岗位、业务类型之间的权限关系。
- 输出标准化鉴权结果。

可读：

- 人员表。
- 公司表。
- 项目权限表。
- 角色权限表。
- 制度相关业务流。

可写：

- 鉴权日志。

禁止：

- 修改业务数据。
- 代替业务 Agent 做业务判断。

### 6.4 内业 Agent

职责：

- 统一执行数据库读写。
- 统一执行文件归档。
- 统一执行对象存储。
- 统一维护业务流转记录。
- 根据上游 Agent 的结构化请求写入对应表。

可读：

- 全量数据库。

可写：

- 全量数据库。
- 文件存储系统。
- 向量库。
- 图数据库。

约束：

- 内业 Agent 不自主改变业务语义。
- 内业 Agent 只根据已鉴权、已确认的业务流转单执行数据操作。

### 6.5 业务 Agent

职责：

- 根据业务制度和业务流模板引导用户完成信息录入。
- 判断必填字段是否完整。
- 调用知识库匹配录入规则。
- 调用多模态能力解析文件、图片、语音内容。
- 生成结构化业务事件。
- 将归档请求提交给内业 Agent。

可读：

- 制度相关业务流。
- 人员表。
- 通讯录。
- 公司表。
- 项目基础表。
- 业务流模板表。

可写：

- 业务流转单草稿。
- 用户补充信息暂存。

禁止：

- 未经内业 Agent 直接写库。
- 未经管理员审核上线新业务流。

## 7. Skill 定义原则

Skill 是 Agent 可调用的标准化能力单元，不应等同于完整 Agent。

### 7.1 Skill 的定位

Skill 应负责一个明确、可复用、边界清晰的能力，例如：

- 生成业务编号。
- 解析计划表。
- 提取文件正文。
- OCR 识别图片。
- 生成事件摘要。
- 匹配事件分类。
- 检查必填字段。

### 7.2 Skill 的约束

1. Skill 原则上不直接写业务数据库。
2. Skill 输入输出必须结构化。
3. Skill 不负责权限判断。
4. Skill 不负责业务最终决策。
5. Skill 可被多个 Agent 复用。

### 7.3 第一阶段推荐 Skill

第一阶段建议优先实现以下 Skill：

| Skill | 作用 |
|---|---|
| 事件编号生成 Skill | 生成 event_id、flow_id、business_no |
| 意图识别 Skill | 从 IM 消息中识别用户意图 |
| 事件分类 Skill | 匹配事件类型 |
| 字段补全检查 Skill | 判断录入信息是否满足规则 |
| 文件解析 Skill | 提取 PDF、DOCX、图片等内容 |
| 计划表解析 Skill | 将计划表转为结构化计划任务 |
| 通知模板 Skill | 生成 IM 通知内容 |

## 8. 基座工具与数据层

### 8.1 DBUtils 数据库网关

DBUtils 是所有 Agent 访问数据库的统一网关，负责：

- 数据库连接管理。
- SQL 执行。
- 权限拦截。
- 操作日志。
- 事务控制。
- 多数据库路由。

原则上 Agent 不直接连接数据库，而是通过 DBUtils 或内业 Agent 间接访问。

### 8.2 PostgreSQL

PostgreSQL 作为第一阶段主数据库，用于存放结构化业务数据。

建议第一阶段采用：

```text
单 PostgreSQL 实例 + project_id 逻辑隔离
```

暂不建议每个项目单独创建数据库文件，以免增加维护复杂度。

### 8.3 MinIO

MinIO 用于存放非结构化文件，包括：

- PDF。
- DOCX。
- PNG/JPG。
- DWG。
- SKP。
- 合同。
- 图纸。
- 施工照片。
- 往来函件。

数据库中只保存文件元数据、对象存储路径、文件指纹、关联业务编号。

### 8.4 FAISS / 向量库

向量库用于存放制度、历史业务流、项目经验、文档片段等可检索知识。

第一阶段可用于：

- 检索制度依据。
- 匹配历史类似事件。
- 匹配业务流模板。
- 辅助未知业务流程生成。

### 8.5 Neo4j

Neo4j 可用于后续构建项目知识图谱和业务流程图谱。

第一阶段不强依赖 Neo4j，但数据设计应保留后续同步空间。

## 9. MVP 业务场景

### 9.1 IM 通讯记录

触发条件：

- 用户在群聊或单聊中发送消息。
- Agent 向用户发送消息。

处理流程：

```text
接收 IM 消息
→ 生成 event_id
→ 结构化消息字段
→ 判断是否关联项目
→ 判断是否包含业务意图
→ 通讯记录归档
→ 如有业务意图则生成业务流转单
```

归档内容：

- 群聊消息。
- 单聊消息。
- 文件消息。
- 图片消息。
- 语音转文字结果。
- Agent 回复内容。

### 9.2 通用业务事件录入

触发条件：

- 用户明确表达“上报、录入、记录、上传、提交”等意图。
- 用户上传文件、图片、表格，并说明其业务含义。
- 路由 Agent 判断消息属于业务事件。

处理流程：

```text
识别事件录入意图
→ 创建业务流转单
→ 鉴权
→ 匹配事件类型
→ 匹配录入规则
→ 引导用户补充字段
→ 多模态解析
→ 合规校验
→ 结构化事件
→ 派发内业 Agent 归档
→ 通知相关人员
```

### 9.3 新建项目

触发条件：

- 管理员或有权限用户提出新建项目。

第一阶段处理方式：

```text
收集项目基本信息
→ 鉴权
→ 校验项目是否重复
→ 创建项目主记录
→ 指定项目负责人
→ 初始化项目权限关系
→ 初始化项目基础目录
```

项目基本信息至少包括：

- 项目名称。
- 项目编码。
- 项目地址。
- 所属城市。
- 项目负责人。
- 建设单位。
- 创建人。

### 9.4 上传计划表

触发条件：

- 用户上传 Excel、表格截图、文档形式的计划表。
- 用户明确表示“录入计划、更新计划、挂起计划、撤下计划”。

处理流程：

```text
接收计划文件
→ 文件归档
→ 解析计划明细
→ 识别责任人、验收人、计划内容、计划完成时间
→ 用户确认解析结果
→ 写入计划主表与明细表
→ 经理 Agent 持续关注到期状态
```

### 9.5 计划任务提醒

触发条件：

- 计划任务到达提醒时间。
- 计划任务超期未完成。
- 计划任务被挂起或替换。

处理流程：

```text
经理 Agent 定时扫描计划任务
→ 识别即将到期或超期任务
→ 通知责任人
→ 必要时通知验收人或项目负责人
→ 记录提醒日志
→ 用户反馈完成后进入销项流程
```

## 10. 自进化业务流机制

自进化能力是本系统的重要特征，但必须受控运行。

### 10.1 触发条件

当路由 Agent 或业务 Agent 无法匹配已有业务流模板时，触发未知业务处理流程。

典型场景：

- 用户提出系统未配置过的业务请求。
- 当前项目制度与历史项目存在差异。
- 既有字段无法满足新业务记录需要。
- 既有通知或归档规则不足。

### 10.2 处理流程

```text
未知业务请求
→ 检索公司制度
→ 检索历史类似项目经验
→ 生成临时业务处理预案
→ 生成字段结构建议
→ 生成数据库存储建议
→ 生成权限建议
→ 提交管理员审核
→ 管理员通过后写入业务流模板库
→ 后续相似请求自动复用
```

### 10.3 管理员审核内容

管理员至少需要确认：

1. 业务流程是否符合公司制度。
2. 权限边界是否合理。
3. 数据字段是否必要且充分。
4. 是否涉及敏感信息。
5. 通知对象是否正确。
6. 是否允许作为正式业务流上线。

### 10.4 上线约束

1. AI 只能生成业务流建议，不能自动上线。
2. 未审核业务流只能作为临时处理方案。
3. 所有管理员审核动作必须留痕。
4. 审核通过后的业务流应版本化管理。
5. 新版本业务流不应破坏历史业务记录。

## 11. 权限与审计

### 11.1 权限原则

系统采用基于角色、项目、公司、业务类型的综合权限判断。

权限判断至少考虑：

- 用户身份。
- 用户所属公司。
- 用户岗位。
- 用户所在项目。
- 业务类型。
- 业务风险等级。
- 是否为管理员。

### 11.2 示例

- 建设单位分管景观的管理者，无权下达室内精装相关任务。
- 工程承包单位的铺装班组，无权新增公司制度。
- 普通施工人员可上报施工事件，但不能修改项目基础信息。
- 项目负责人可查看本项目大部分业务记录，但不能查看其他项目敏感信息。

### 11.3 审计要求

所有关键操作必须留痕，包括：

- 消息接收。
- 意图识别。
- 鉴权结果。
- 用户补充信息。
- 文件上传。
- 数据写入。
- 通知发送。
- 异常处理。
- 管理员审核。
- 业务流版本变更。

## 12. 数据库设计原则

### 12.1 第一阶段数据库策略

第一阶段建议采用统一数据库、多项目逻辑隔离方式：

```text
一个 PostgreSQL 主库
通过 project_id 区分不同项目
通过权限系统限制可见范围
```

暂不建议每个项目单独创建数据库文件。

### 12.2 核心表建议

第一阶段建议优先实现以下核心表：

| 表名 | 用途 |
|---|---|
| im_message | IM 通讯记录统一表 |
| employee | 人员信息表 |
| company_info | 公司基础信息表 |
| project_basic | 项目基础信息表 |
| project_indicator | 项目指标表 |
| business_flow_instance | 业务流实例表 |
| business_flow_log | 业务流日志表 |
| project_event | 项目事件主表 |
| file_object | 文件元数据表 |
| plan_main | 计划主表 |
| plan_item | 计划明细表 |
| permission_rule | 权限规则表 |
| business_flow_template | 业务流模板表 |
| admin_review_record | 管理员审核记录表 |
| incident_record | 异常记录表 |

### 12.3 通讯记录表策略

第一阶段建议使用统一 `im_message` 表，不拆分群消息表和单聊消息表。

通过以下字段区分：

- `conversation_type`：group/private。
- `group_id`：群聊时有值。
- `receiver_id`：单聊时有值。
- `direction`：user_to_agent / agent_to_user。

这样可以降低第一阶段开发复杂度，后续数据量增大后再考虑分区或拆表。

## 13. 第一阶段实施优先级

建议按以下顺序实施：

### 阶段一：消息接入与记录

目标：让系统先能稳定接收、记录、回复 IM 消息。

范围：

- AstrBot IM 对接层。
- 路由 Agent 最小实现。
- `event_id` 生成。
- `im_message` 入库。
- Agent 回复消息下发。

### 阶段二：业务流转单与鉴权

目标：建立 Agent 协同的核心协议。

范围：

- 业务流转单结构。
- 鉴权 Agent。
- 内业 Agent 基础读写接口。
- 操作日志。

### 阶段三：通用事件录入

目标：实现第一个可复用业务流。

范围：

- 事件分类。
- 必填字段引导。
- 多轮补全。
- 事件结构化。
- 文件归档。
- 项目事件入库。

### 阶段四：计划任务与提醒

目标：实现计划表录入和经理 Agent 提醒能力。

范围：

- 计划表解析。
- 计划主表与明细表。
- 到期扫描。
- IM 提醒。
- 销项记录。

### 阶段五：自进化业务流

目标：实现未知业务需求的受控学习机制。

范围：

- 未知业务识别。
- 临时预案生成。
- 管理员审核。
- 业务流模板入库。
- 版本管理。

## 15. 结论

团队大脑 Agent 模块的第一阶段重点不是穷举所有地产开发业务清单，而是先建立一套可运行的基础框架：

```text
IM 接入
→ 路由识别
→ 鉴权
→ 业务流转单
→ 专项 Agent 处理
→ 内业 Agent 归档
→ 经理 Agent 监控
→ 未知业务受控进化
```

只要该框架成立，后续施工、设计、成本、证照、会议、计划、文件、合同等业务都可以逐步作为业务流模板沉淀进系统。
