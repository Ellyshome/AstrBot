# 技术架构设计

## 1. 设计目标

本文件用于指导团队大脑 Agent 模块第一阶段开发。目标不是一次性完成完整地产开发业务系统，而是先实现一个能稳定运行的最小闭环：

```text
IM 收到消息
→ 标准化消息
→ 生成 event_id
→ 写入通讯记录
→ 路由 Agent 判断意图
→ 必要时生成 flow_id 和业务流转单
→ 鉴权
→ 业务 Agent 引导录入
→ 内业 Agent 入库
→ IM 回复用户
```

第一阶段坚持以下原则：

1. 能跑通优先，复杂能力后置。
2. 先实现单机/单进程可运行版本，后续再拆服务。
3. 先使用 PostgreSQL 做主数据存储，MinIO/向量库可逐步接入。
4. Agent 之间通过结构化对象传递，不直接互相修改内部状态。
5. 所有关键动作保留日志，便于后续排错和审计。

## 2. 总体架构

```text
AstrBot / IM 平台
  ↓
团队大脑插件入口
  ↓
IM 消息标准化层
  ↓
路由 Agent
  ├─ 鉴权 Agent
  ├─ 业务 Agent
  ├─ 内业 Agent
  └─ 经理 Agent
  ↓
DBUtils 数据库网关
  ↓
PostgreSQL / MinIO / FAISS
```

第一阶段建议所有 Agent 都作为同一 Python 项目内的模块运行，不必拆成多个独立服务。

## 3. 模块划分

建议代码按以下模块组织：

```text
team_brain/
  plugin.py                  # AstrBot 插件入口
  config.py                  # 配置加载
  core/
    ids.py                   # event_id / flow_id 生成
    schemas.py               # 核心数据结构
    logger.py                # 日志封装
  im/
    adapter.py               # IM 消息标准化与下发适配
    message_types.py         # 消息类型定义
  agents/
    router_agent.py          # 路由 Agent
    auth_agent.py            # 鉴权 Agent
    business_agent.py        # 通用业务 Agent
    archive_agent.py         # 内业 Agent
    manager_agent.py         # 经理 Agent
  workflows/
    base.py                  # LangGraph 基础封装
    im_record_flow.py         # 通讯记录流程
    event_record_flow.py      # 通用事件录入流程
    plan_flow.py              # 计划任务流程，后续实现
  db/
    db_utils.py              # 数据库网关
    repositories.py          # 数据表读写方法
    migrations/              # 建表脚本，后续可接 Alembic
  skills/
    intent_detect.py          # 意图识别
    event_classify.py         # 事件分类
    field_check.py            # 字段完整性检查
    file_parse.py             # 文件解析，后续增强
    notify_template.py        # 通知模板
```

如果前期只想更快跑通，也可以先减少目录，只保留：

```text
plugin.py
schemas.py
router_agent.py
auth_agent.py
business_agent.py
archive_agent.py
db_utils.py
```

## 4. AstrBot 对接方式

第一阶段以 AstrBot 插件形式接入。

插件入口只做三件事：

1. 接收 AstrBot 转来的 IM 消息事件。
2. 调用团队大脑内部 `handle_im_message()`。
3. 将处理结果通过 AstrBot 消息接口发回用户或群。

插件入口不直接写数据库、不直接判断复杂业务。

示意流程：

```text
AstrBot 收到消息
→ plugin.py:on_message
→ im.adapter.normalize_message
→ router_agent.handle
→ 返回 reply
→ plugin.py 发送 reply
```

## 5. IM 消息标准化

所有 IM 消息进入系统后，应转换为统一结构。

```json
{
  "event_id": "EV-20260605-00001",
  "im_source": "qq",
  "conversation_type": "group",
  "conversation_id": "group_001",
  "group_id": "group_001",
  "sender_id": "user_001",
  "sender_name": "张三",
  "receiver_id": null,
  "msg_type": "text",
  "content": "今天1号楼地下室防水验收完成",
  "files": [],
  "timestamp": "2026-06-05T10:00:00"
}
```

第一阶段支持的消息类型：

| 类型 | 说明 |
|---|---|
| text | 文本消息 |
| image | 图片消息，先记录文件引用，OCR 后置 |
| file | 文件消息，先存文件元数据，解析后置 |
| voice | 语音消息，第一阶段可只记录文件 |

## 6. 核心 ID 生成

### 6.1 event_id

每条进入系统的 IM 消息都应绑定一个 `event_id`。

格式：

```text
EV-YYYYMMDD-000001
```

### 6.2 flow_id

当消息触发业务流程时，生成 `flow_id`。

格式：

```text
FLOW-YYYYMMDD-000001
```

### 6.3 business_no

业务事件正式入库时，可生成业务编号。

格式：

```text
BUS-YYYYMMDD-000001
```

第一阶段可以使用数据库自增序列或时间戳加随机数生成，后续再统一为雪花 ID 或专用编号服务。

## 7. 业务流转单结构

Agent 之间通过业务流转单传递上下文。

```json
{
  "event_id": "EV-20260605-000001",
  "flow_id": "FLOW-20260605-000001",
  "flow_type": "event_record",
  "source": "im",
  "status": "processing",
  "user": {
    "user_id": "user_001",
    "user_name": "张三"
  },
  "project": {
    "project_id": null,
    "project_name": null
  },
  "intent": {
    "intent_type": "event_record",
    "confidence": 0.8,
    "raw_text": "今天1号楼地下室防水验收完成"
  },
  "payload": {},
  "auth_result": {},
  "logs": []
}
```

## 8. Agent 调用关系

### 8.1 路由 Agent

入口 Agent，负责：

1. 接收标准化 IM 消息。
2. 调用内业 Agent 保存通讯记录。
3. 调用意图识别 Skill。
4. 判断是否需要发起业务流。
5. 分派给对应 Agent。

第一阶段意图类型建议只支持：

| intent_type | 说明 |
|---|---|
| chat | 普通聊天/普通记录 |
| event_record | 业务事件录入 |
| plan_record | 计划任务录入 |
| query | 信息查询，后续实现 |
| unknown | 未知意图 |

### 8.2 鉴权 Agent

第一阶段先实现最小鉴权：

1. 系统能识别用户是否存在。
2. 用户是否被允许访问对应项目。
3. 用户是否具有当前业务类型权限。

如果权限表未配置，第一阶段可采用保守策略：

```text
普通信息记录允许
项目主数据修改拒绝
未知业务流提交管理员审核
```

### 8.3 业务 Agent

第一阶段先实现通用事件录入 Agent。

职责：

1. 判断事件类型。
2. 抽取项目、时间、地点、人物、事项。
3. 检查是否缺少关键信息。
4. 如信息不足，生成追问内容。
5. 信息足够时生成结构化事件。

### 8.4 内业 Agent

统一数据读写入口。

职责：

1. 保存通讯记录。
2. 保存业务流实例。
3. 保存业务流日志。
4. 保存项目事件。
5. 保存文件元数据。
6. 保存异常记录。

第一阶段不要求内业 Agent 自动推理表结构，只按既有表写入。

### 8.5 经理 Agent

第一阶段只实现最小能力：

1. 扫描计划任务到期情况。
2. 记录异常事件。
3. 对未知业务流产生管理员提醒。

## 9. LangGraph 使用策略

第一阶段不需要把所有流程都复杂图谱化。

建议只对以下流程使用 LangGraph：

1. 通用事件录入流程。
2. 计划任务录入流程。
3. 未知业务流审核流程。

通讯记录可以先用普通函数流程实现。

通用事件录入图：

```text
start
→ classify_event
→ auth_check
→ extract_fields
→ check_required_fields
→ need_more_info?
  ├─ yes → ask_user → waiting_user_reply
  └─ no  → archive_event → notify_user → end
```

## 10. 数据库访问策略

第一阶段统一通过 `DBUtils` 访问数据库。

DBUtils 至少提供：

```text
execute(sql, params)
fetch_one(sql, params)
fetch_all(sql, params)
transaction()
```

后续可逐步封装 Repository，例如：

```text
MessageRepository
FlowRepository
EventRepository
PlanRepository
PermissionRepository
```

## 11. 文件存储策略

第一阶段可以先记录文件元数据和本地/AstrBot 文件路径。

后续接入 MinIO 后，再将文件统一转存到对象存储。

文件记录至少包括：

- file_id
- original_name
- file_type
- file_size
- storage_path
- uploader_id
- event_id
- flow_id

建议提供基础配置：

```yaml
team_brain:
  enabled: true

    url: "postgresql://user:password@localhost:5432/team_brain"

    level: "INFO"
```

## 13. 日志与异常

所有关键步骤应记录日志：

- 收到 IM 消息。
- 生成 event_id。
- 通讯记录入库。
- 意图识别结果。
- 鉴权结果。
- 业务流创建。
- 事件入库。
- 回复用户。
- 异常信息。

异常处理原则：

1. 用户侧提示要简洁。
2. 系统侧日志要完整。
3. 数据库写入失败不得静默吞掉。
4. 未知异常写入 `incident_record`。

## 14. 第一阶段最小闭环

建议第一轮开发只跑通：

```text
用户发送：记录一下，今天1号楼地下室防水验收完成。
系统处理：
1. 接收消息
2. 生成 event_id
3. 保存 im_message
4. 识别为 event_record
5. 生成 flow_id
6. 创建 business_flow_instance
7. 鉴权通过
8. 抽取事件内容
9. 写入 project_event
10. 回复：已记录该事件
```

如果能跑通该闭环，后续计划任务、文件解析、自进化业务流都可以在此基础上扩展。

## 15. 后续扩展方向

第一阶段完成后，再逐步扩展：

1. 多轮补全。
2. 文件解析。
3. 计划表解析。
4. MinIO 文件归档。
5. FAISS 制度检索。
6. 自进化业务流审核。
7. Neo4j 业务关系图谱。
8. 多项目权限隔离增强。
